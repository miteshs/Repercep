Executive summary

The Repercep.AI runtime is a vendor-neutral serving layer for world models. It now serves all three workload regimes through one backend seam: two flavors of the control regime — energy-based, action-conditioned planning (V-JEPA 2-AC class, output is plans reached by search) and policy-driven video-action serving (LingBot-VA, DreamZero class, output is plans generated directly by the model) — plus the generation regime (Cosmos, Wan video diffusion). Both control regimes are the strategic lead: closed-loop, state-carrying serving is a workload we believe nobody else publishes a leaderboard for, and this report now includes measured cross-vendor numbers for both control mechanisms, not just one.

2Energy-based control: V-JEPA 2-AC (the original strategic lead)

V-JEPA 2-AC (Meta) is the flagship of the energy-based, action-conditioned camp of world models: a robot controller rolls the world forward in latent space and plans actions by minimizing an energy function (CEM/MPC). No pixel decode, no diffusion — a fundamentally different serving problem from video generation, and one no serving stack (including NVIDIA's NIM) currently optimizes. To our knowledge this was the first published cross-vendor latency profile for this workload.

The silicon gap is small (7% on the step, 17–21% on the plan) and the naive planner is far too slow for closed-loop control — robot control loops need 10–100 ms per decision, and a stock CEM plan costs tens of seconds. CEM-candidate batching (all 64 candidates as one forward per timestep) closes part of that gap at planning-quality parity:

Finding — and why it de-risked the roadmap

This redirected optimization toward KV/latent reuse and a bf16 predictor path — exactly the class of lever the two policy-driven models in §3 validate independently, on a different architecture.

3Policy-driven control: LingBot-VA and DreamZero (the second control regime)

Energy-based control (§2) searches for a plan by minimizing an energy function over sampled rollouts. The second control mechanism is structurally different: a policy-driven video-action model generates its own next action chunk directly — the denoise loop is the planner, with no external CEM/MPC search. Two models validate this regime end-to-end this cycle, on real camera input, not synthetic pixels: LingBot-VA 2.0 (Ant Group/Robbyant, MoT DiT over Wan2.2 latents) and DreamZero-DROID (16.5B, Wan2.1-based, attached to NVIDIA's GR00T 2 ecosystem). Both regimes now run under the identical closed-loop harness — state carryover required, warm-vs-cold disclosed — so all numbers in §2 and this section are directly comparable.

Portable, config-only levers (CFG reduction + fewer action-denoise steps, zero CUDA-locked tooling) take the H100 chunk latency to 342.2 ms — 2.0× the baseline — roughly halfway across the model's own published 927→466 ms "portable techniques" band, on top of an already-optimized starting point. That same lever config nearly doubles session density (11→24 measured, not extrapolated, with no per-session latency penalty up to the memory ceiling). The honest caveat: the CFG-reduction lever measurably shifts the model's action-output distribution on specific channels (one channel's p50 drops ~99%) — the latency and memory wins are real and measured; task-correctness of the resulting policy is not validated (no offline success metric exists for this model in our harness).

DreamZero-DROID

DreamZero is the larger of the two policy models (16.5B parameters vs. LingBot-VA's mid-size DiT) and the first model on our seam attached to the GR00T ecosystem. Finding — the clearest capacity story measured yet

DreamZero's per-session memory cost (~23 GiB, nearly identical across vendors) is roughly 4× LingBot-VA's — large enough that H100 holds exactly one resident session at full attention-window compute, confirmed empirically (a live 2-session run exhausted H100's 80 GiB mid-forward-pass, not merely an extrapolation). MI300X's 192 GiB headroom converts that into six resident sessions on the same unmodified engine code — the cleanest measured instance yet of large-memory silicon turning a hard capacity ceiling into serving headroom.

A second, unexplained result: DreamZero's MI300X chunk latency measured slightly faster than H100 (5646.6 vs 5890.6 ms) — the opposite of LingBot-VA's 1.59×-slower MI300X row. One run each; a repeat run to confirm this ordering is open work, stated here rather than smoothed over.

Caveats — stated here, not in a footnote

The model's own published latency claim is not full compute. DreamZero's reference implementation silently defaults to a static 8-of-16 DiT-step skip with no opt-in flag required — measured at 3068.8 ms/chunk on H100, 1.85× faster than the 5890.6 ms full-compute number in the table above. Both are real, measured numbers; they are not the same baseline, and this report states which is which rather than letting the faster one stand in for both. A dynamic cosine-similarity DiT-cache schedule we measured reaches 1780.2 ms — 3.19× the true baseline, faster than every static skip level.

Parity vs. the reference server is not yet validated. Our engine reimplements the reference model's input-construction and denormalization logic directly (verified line-by-line against the published source), but a literal side-by-side run against the reference's own serving stack on held-out evaluation data has not been completed — it requires a dataset-transform dependency chain (GR00T-N1.5's ComposedModalityTransform) we deliberately have not vendored. This report's DreamZero numbers are latency, memory, and session-density claims; they are not yet an independent correctness claim.

4Generation regime: Cosmos-Predict-7B

The generation benchmarks demonstrate two things: that our optimizations are vendor-neutral by construction, and that its results reproduce across sessions, stacks, and months. The workload is the model's reference configuration: 121 frames at 1280×704, 36 denoising steps, BF16.

Reproducibility. The June re-run reproduced the May numbers on fresh instances and different driver stacks (154.0 vs 154), and repeat runs in May varied by ±0.5%. Same-seed generations are bit-identical (MD5-verified) across sessions.

The deployable path is near vendor parity. On the cache-accelerated path customers would actually run, MI300X is within 10% of H100. The wider 1.29× baseline gap in June is a stack artifact (untuned ROCm 6.3 attention), not silicon — the tuned May run measured the raw silicon gap at ~5–22% depending on configuration.

Cost per video favors AMD. At current rental prices, one reference video costs $0.094 on MI300X vs $0.127 on H100 — 26% cheaper — on the adaptive path.

Against NVIDIA's own published H100 reference for this model (~380 s, their optimized CUDA-only stack), our cached path is 2.7× faster on H100 and 2.5× faster on MI300X. That is a shipped-system vs shipped-system comparison, and it needs two caveats:

Caveats — stated here, not in a footnote

The 2.5–2.7× is a system comparison, not a hardware claim. NVIDIA's published path has no adaptive cache; ours does. At identical compute (no cache), MI300X measured 1.2× slower than NVIDIA's published H100 number. The legitimate claim is that our runtime ships an optimization NVIDIA's documented serving path lacks — on both vendors — not that AMD hardware outruns H100.

The adaptive cache is a quality/speed trade-off, not a free lunch. Cached output is a different valid generation of the same prompt (pixel-level LPIPS 0.645 vs the uncached reference, with ~28–30% reduced inter-frame motion at the speed-biased default threshold). Distribution-level quality evaluation (FVD at N≥50) is open work, gated before any external publication of the speed-vs-quality story.

5Generation regime: Wan-2.2-T2V-A14B

Wan-2.2 (Alibaba's 14B-active MoE video model) exercises the runtime at the memory limit. Our runtime runs the canonical 81-frame / 40-step shape on a single H100 in 1,552.8 s at 72.6 GiB — a fit that requires our VAE-tiling path, since the both-experts-resident model does not otherwise fit in 80 GB — and on MI300X (~1,700 s projected steady-state at 85.1 GiB) with no tiling needed, the 192 GB part absorbing it natively.

The Wan team's own H100 reference (1,041.5 s) uses CPU offload plus FP8 weight conversion we have not yet wired, so it is not apples-to-apples with our number; matching that configuration is known, unglamorous work. The relevant takeaway is the pattern: the same unmodified engine code produced both vendors' numbers, and large-memory silicon converts an engineering workaround (tiling, offload) into headroom — the same pattern DreamZero's session-density result (§3) now shows for the control regime too.

7Methodology and known limitations

The full protocol is in docs/METHODOLOGY.md and docs/CONTROL_LOOP_BENCH.md, written deliberately for a skeptical reader. The short version: every headline is a wall-clock measurement from a scripted harness emitting a JSON result line (archived verbatim in the repo); model-load time is excluded from steady-state numbers, mirroring NVIDIA's disclosure convention; ROCm's first-run kernel-autotuning cost (~3× on a cold forward for generation-regime models, up to ~8× observed on DreamZero's first call) is measured, disclosed, and excluded via warm-up separation. State carryover is required for every closed-loop number: one session stays alive across all timed steps, matching how these models are actually served, not a fresh-session-per-call number that would structurally favor request/response framing.

Limitations we track openly:

  • Single prompt/seed for most headline timings. Run-to-run variance measured at ±0.5% across sessions for generation-regime numbers, but multi-prompt variance and an N=10 timing distribution remain open for the control regimes. DreamZero's MI300X-vs-H100 latency ordering (§3) is a single run each and explicitly flagged as unconfirmed.
  • Cache quality is quantified only at pixel level so far. FVD over a ≥50-clip held-out set is the defined gate before publishing the Cosmos speed-vs-quality claim externally; tooling is built, generation of the reference set is pending.
  • Policy-regime task-correctness is not independently validated. LingBot-VA's CFG-reduction lever measurably shifts action-output distribution (§3); DreamZero's numbers are not yet checked against the reference server on held-out evaluation data (§3). Both are latency/memory/capacity claims, not correctness claims, until that work lands.
  • The May MI300X generation-regime numbers were taken on a virtualized (VF) slice; a bare-metal confirmation run is planned. DreamZero's MI300X row (§3) was also taken on a virtualized slice (AMD Developer Cloud).
  • "First publicly reported" claims are claims about the state of public disclosure on the date made (we catalog exactly where we searched), not global novelty claims — and we commit to updating, not arguing, if prior art surfaces.

8What the numbers say, in one paragraph

World models split into two control mechanisms and one generation regime, and this report now has measured, cross-vendor numbers for all three on the same unmodified engine code. The energy-MPC control regime is vendor-agnostic (7% silicon gap) and structurally under-served (a 55-second plan against a 100 ms budget) — the product roadmap, not a risk disclosure. The policy-driven control regime, new this cycle, adds a second proof point that closed-loop serving is real and portable: LingBot-VA reaches a 2.0× latency win from config-only levers, and DreamZero shows the clearest capacity story measured yet — six resident sessions on MI300X against one on H100, on a 16.5B model neither vendor's stock serving path currently optimizes. The generation-regime results — 3.2–3.8× reproduced on both vendors — remain the proof that the runtime and its methodology are real. What is not yet done is stated as plainly as what is: DreamZero's parity against its own reference server, and task-correctness validation for the levers that trade latency for distributional shift. Measurement, not intuition, decides both next.
