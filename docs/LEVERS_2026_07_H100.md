# V-JEPA 2-AC latency levers — measured on H100 (2026-07-11)

GPU verification + first measurements of the three levers that landed in
`models/vjepa2_ac.py` today (`scripts/bench_vjepa2_ac_levers.py`, RunPod H100
SXM, torch 2.9.1+cu128, transformers 4.56.2, same CEM budget as the June
baseline: 64 samples × 3 iters, H=4). All rungs measured on the same box in the
same process — cross-doc absolute numbers differ from `BENCH_2026_06_RUNPOD.md`
(68.8 s vs 55.6 s sequential) because the stack differs; the *ratios* are the
result.

## The ladder

| plan config (H=4, 64×3) | seconds | vs sequential |
|---|---|---|
| sequential, fp32 (shipped baseline) | 68.84 | 1.0× |
| + candidate batching (fp32) | 40.58 | 1.7× |
| + bf16 predictor (batched) | **9.42** | **7.3×** |
| + warm start (steady-state replan, 1 iter — see below) | **~3.1 (est)** | **~22×** |

- **bf16 parity: max relative energy difference vs fp32 = 0.0000** on identical
  candidate sets (energies agree to bf16 resolution). The SDPA dtype
  harmonizer is GPU-verified; the fp32 tax identified in June is retired
  as an *opt-in* config (`predictor_compute_dtype="bfloat16"`).
- **bf16 is a batch-size story:** single-step latency barely moves (89.8 →
  84.9 ms — batch-1 forwards are launch/memory-bound), but at batch-64 the
  forward is compute-bound and bf16 delivers 4.3× on top of batching. This
  refines the June finding: batching alone was "only" 1.7× because fp32 was
  the ceiling; the two levers *compose*.
- **Warm start changes the iteration economics, not the per-iter cost:** at a
  1-iteration budget the warm replan reaches energy **30.25** vs cold-1-iter
  40.25 — and beats the *full 3-iteration cold plan* (45.0), because it starts
  from the previous converged solution shifted one step. Steady-state
  receding-horizon replanning can therefore run at ⅓ budget with better plans:
  9.42 s / 3 ≈ **~3.1 s per replan** (estimate; per-iter timing not measured
  separately).
- Peak HBM 12.7 GiB with both engines (fp32 + bf16 predictors) resident.

(The 385 s fp32 "load" includes the one-time 11 GB AC-checkpoint download;
the bf16 engine's 29.1 s load reuses the cache and is the honest load number.)

## Where this leaves the 6-week latency commitment

June baseline 55.6 s → today's measured 9.42 s cold plan / ~3.1 s warm replan
on H100, with **no model change and no CUDA-only machinery** (plain SDPA —
the whole ladder ports to ROCm). The remaining gap to sub-second is the
context-window recompute: every rollout step reprocesses the full ~2048-token
window. That is the KV/latent-reuse workstream (the June-ranked #1 lever,
now the only big one left), tracked as the publishable mechanism.
